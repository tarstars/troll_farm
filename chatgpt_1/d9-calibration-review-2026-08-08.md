The committed evidence is sufficient to establish the central semantic finding:
`banana_before_train` is not a valid detector for second-worker TRAIN displacement and should be
retired rather than waived. It is an unpaired temporal proxy that fires on parent behaviour even
when the candidate and parent TRAIN schedules are identical.

The current package is **not yet sufficient to adopt the repaired D-9 or to publish the claimed

1. parent-vs-parent identity is inferred from equal terminal summaries rather than bound to exact

2. `blocking_games_without_d9` ignores non-detector blocking violations, including P4 liveness;
3. the retained paired clauses have a negative control but no positive bite-test.

Until those are closed, D-9 is a materially miscalibrated required detector. Under the standing
gate architecture, that means `GATE_UNREADY`, not PASS and not report-only.

## Accepted finding: the proxy is semantically wrong

`detect_d9()` currently mixes two different predicates:

- paired predicates comparing the candidate's first TRAIN with the parent's first TRAIN:
  `train_late`, `train_missing`, and `train_stats_differ`;
- an unpaired predicate, `banana_before_train`, which fires whenever a one-worker candidate issues
  an own `PICK BANANA` or `PLANT BANANA` before its own first TRAIN.

The proxy never reads the parent. Therefore it cannot distinguish:

- banana work that displaced TRAIN;
- banana work that the parent also performs without changing TRAIN;
- a game in which neither side ever trains;
- a candidate that performs a harmless PICK/PLANT pair and then trains on the exact parent turn.

The floor package records exactly the second case: the resident's established PICK/PLANT orchard
sequence. A candidate cannot be later than itself. Subject to the provenance repair below, 196
proxy episodes in a true parent-vs-parent run are false positives by construction.

The correct semantic repair is therefore:

1. delete `banana_before_train` from D-9;
2. retain the direct paired predicates;
3. do **not** add a parent-behaviour exemption around the proxy, because that would recreate the
   rejected parent-differential gate rather than repair the predicate.

This direction is accepted independently.

## Blocking finding D9-R1 — parent identity is not provenance-bound

The analyzer defines parent-vs-parent as:

```python
is_parent_vs_parent = all(
    g.get("candidate") == g.get("parent") for g in games
) and bool(games)
```

Here `candidate` and `parent` are terminal summary dictionaries. Equal terminal summaries do not
prove that the same source, binary, configuration or command stream was used. Two different bots
can finish with equal score/inventory summaries; a faulty harness can also write the same terminal
summary to both fields while commands differ.

The input JSON is named and described as a parent-vs-parent floor self-test, but the calibration
result needs a machine-checkable identity proof because that premise carries the entire causal
argument. Required provenance:

- exact source SHA-256 for candidate and parent, equal;
- exact compiled-binary SHA-256 for candidate and parent, equal, or one shared binary path/hash;
- exact panel/config/map/opponent/detector hashes;
- per-game candidate and parent command-stream hashes, equal for the negative control;
- explicit `comparison_kind: parent_vs_parent` generated by the harness, not inferred from
  terminal equality;
- analyzer failure if any required identity field is absent or unequal.

The existing terminal equality may remain as a consistency check, but not as the identity proof.
The committed tests currently pin terminal equality only; they need a bite-test showing that equal
terminal summaries with unequal source or command hashes are rejected.

## Blocking finding D9-R2 — the reported 118 → 46 floor is under-specified

The analyzer computes the residual floor as:

```python
without_d9 = [
    i for i in blocking
    if any(c for d, c in (games[i].get("detector_counts") or {}).items()
           if d != "D-9")
]
```

This answers: “in how many currently blocking games did another numbered detector fire?” It does
**not** answer: “in how many games would the full gate still block after removing only D-9?”

The panel can block on violations not represented in `detector_counts`. P4 liveness is the concrete
known example: a game can contain a blocking `{"property": "P4", ...}` violation without a
`detector` key. Such a game is incorrectly counted as cleared when D-9 is its only numbered
detector, even though P4 still blocks.

The repaired computation must operate on the full violation set:

```text
remaining = [v for v in game.violations if v.detector != "D-9"]
would_block_without_d9 = any(is_blocking(v) for v in remaining)
```

`is_blocking` must use the canonical panel's property/verdict semantics, not infer blocking from
presence of a detector count. Alternatively, replay the canonical evaluator with only the D-9
result removed. The report must publish:

- games blocked before removal;
- games blocked after removing only D-9;
- games for which D-9 is the sole full-gate blocker;
- the complete residual property/detector histogram;
- games versus episodes as separate quantities.

Add a synthetic test where a game has D-9 plus a P4 violation and zero other detector counts; the
post-retirement floor must retain that game. Until this is done, `46` and the claimed 61% reduction
must not be used in a gate or planning decision.

## Blocking finding D9-R3 — the retained clauses have no positive bite evidence

Zero paired-clause episodes in parent-vs-parent is the right negative control. It proves only that
those clauses are silent when candidate and parent TRAIN records match. It does not prove they can
fire when displacement exists, parse the correct turn, or distinguish the intended cases.

The repaired D-9 needs at least these executable fixtures against the real trace/parser path:

1. parent trains at turn `t`, candidate trains at `t+1` with equal stats → exactly one
   `train_late` episode with the correct interval;
2. parent trains, candidate never trains → exactly one `train_missing` episode;
3. both train on the same turn with unequal tuples → exactly one `train_stats_differ` episode
   containing both tuples;
4. both train on the same turn with the same tuple → zero episodes;
5. candidate performs pre-TRAIN banana PICK/PLANT but trains identically → zero episodes after the
   proxy is retired;
6. parent never trains and candidate never trains → explicit expected status, not accidental PASS;
7. parent command input absent → `UNPROVEN`/error for D-9, because a paired displacement detector
   cannot be evaluated without its reference.

The last two cases require a design decision. My recommendation is fail-closed at the gate layer:
D-9 returns an evaluation-status field and the gate reports `UNPROVEN` when parent commands or a
parent TRAIN opportunity are absent, unless the frozen protocol explicitly defines those cases as
not applicable.

## Required adoption sequence

1. Bind the floor input to exact candidate/parent source, binary, command, panel and detector
   hashes.
2. Recompute the residual floor from all blocking violations, not `detector_counts` alone.
3. Add positive and negative bite-tests for every retained paired clause.
4. Edit `detect_d9()` to remove only `banana_before_train` and to expose evaluability status.
5. Re-run the hash-pinned parent-vs-parent negative control and the bite-tests.
6. Obtain independent review of the detector diff and regenerated result.
7. Only then mark the repaired D-9 active and quote a post-retirement floor.
