# Specification: GitHub-native publication gateway for interactive agents

Date: 2026-08-22
Status: **architecture frozen; implementation not started**
Task id: `20260822-github-native-agent-publication-gateway`
Phase: bootstrap while Git remains authoritative

## 1. Purpose

Some agent runtimes can read and write through the connected GitHub API but do not reliably have a persistent checkout, Git index, Python interpreter, shell, or repository-local transport tools. The current protocol treats those capabilities as mandatory for every writing agent. That leaves connector-only agents either read-only or tempted to create ad hoc self-publishing workflows.

The gateway provides one narrow, audited publication operation. It accepts a typed request through GitHub, validates it with current `main`, publishes to the caller's canonical agent branch, verifies the remote result, and returns the exact commit identity.

This is a compatibility adapter, not a second coordination authority. During phase 1, Git messages and branches remain authoritative.

## 2. Phase-1 GitHub interface

### 2.1 Request channel

Use a repository issue as the request envelope because the connected GitHub capability can create and read issues without a local checkout.

A request is eligible only when all are true:

- repository is exactly `tarstars/troll_farm`;
- issue has the configured label `agent-publication-request`;
- issue author is in an explicit owner/operator allowlist, initially only `tarstars`;
- title begins `[agent-publish chatgpt_1]`;
- body contains exactly one JSON object conforming to `coordination/gateway/request-schema-v1.json`;
- request fixes `actor` to `chatgpt_1` and target branch to `agent/chatgpt_1`.

The issue author authenticates the owner-mediated interactive request. The agent identity is fixed by gateway configuration, not trusted from arbitrary body text. A later GitHub App may provide stronger per-agent credentials without changing the request semantics.

### 2.2 Worker

One permanent workflow, `.github/workflows/agent-publication-gateway.yml`, handles eligible issues. It calls a tested Python implementation, `scripts/agent_publication_gateway.py`. The workflow contains no publication logic beyond checking out current `main`, installing nothing, and invoking the script.

The workflow must never evaluate request content as shell. JSON values are passed through files or safe process arguments. `pull_request_target` is forbidden.

### 2.3 Result channel

The worker posts one terminal issue comment containing a JSON result and applies exactly one terminal label:

- `agent-publication-succeeded`; or
- `agent-publication-failed`.

On success it closes the issue. On retry it returns the existing terminal result rather than publishing again.

## 3. Request schema

Top-level fields:

```json
{
  "schema_version": 1,
  "request_id": "stable caller-generated id",
  "actor": "chatgpt_1",
  "operation": "publish_message | publish_handoff",
  "base_main_commit": "40 lowercase hex",
  "expected_agent_head": "40 lowercase hex or null",
  "message": {
    "type": "ack | progress | question | blocker | policy | handoff | release | update | correction",
    "task_id": "exact task id",
    "to": ["agent ids"],
    "cc": ["agent ids"],
    "requires_ack": true,
    "ack_for": ["exact published message paths"],
    "supersedes": ["exact published message paths"],
    "title": "plain title",
    "body_markdown": "human-readable body"
  },
  "artifacts": [
    {
      "path": "chatgpt_1/...",
      "content_utf8": "complete content",
      "expected_absent": true
    }
  ]
}
```

Rules:

- `publish_message` requires an empty `artifacts` list and forbids message type `handoff`.
- `publish_handoff` requires message type `handoff` and at least one artifact.
- `created_utc`, filename timestamp, `message_id`, `from`, `artifact_ref`, and `artifact_commit` are generated by the gateway.
- The gateway renders both v2 front matter and the legacy block from one typed structure. The request cannot supply two divergent representations.
- `expected_agent_head` provides compare-and-swap protection. `null` is allowed only for the first controlled bootstrap test; normal operation requires the exact observed remote head.
- `base_main_commit` must equal the current remote `main` at processing time. Stale requests fail and may be resubmitted with a new request id.

## 4. Allowed writes

The gateway may push only a fast-forward commit or commit pair to `agent/chatgpt_1`.

Allowed artifact prefixes:

- `chatgpt_1/`

Allowed generated message prefix:

- `coordination/messages/chatgpt_1/`

Allowed generated audit prefix:

- `chatgpt_1/gateway-audit/`

Forbidden regardless of request content:

- `main` or any branch other than `agent/chatgpt_1`;
- `.github/`;
- `scripts/`;
- `coordination/tasks/`;
- `coordination/status/`;
- `coordination/messages/<anyone-other-than-chatgpt_1>/`;
- `cgauto/submissions/`;
- the byte-sacred resident source;
- paths containing `..`, absolute paths, empty components, control characters, or normalization changes;
- symlinks, submodules, executable modes, and binary/base64 artifacts in phase 1.

A later task may widen the allowed artifact set. This specification does not.

## 5. Publication transaction

### 5.1 Common preflight

1. Fetch with pruning and an explicit refspec for `main` and canonical agent refs.
2. Verify current `main` equals `base_main_commit`.
3. Verify current `agent/chatgpt_1` equals `expected_agent_head` when supplied.
4. Verify the workflow and Python implementation are from current `main`.
5. Validate request schema, operator identity, fixed actor, operation, paths, recipients, referenced messages, and size limits.
6. Compute a canonical JSON payload hash.
7. Check the audit namespace and terminal issue comments for `request_id`.
   - same id + same payload hash: return the prior result;
   - same id + different hash: fail as an idempotency collision.

### 5.2 `publish_message`

1. Generate server UTC timestamp and immutable message path.
2. Render v2 and legacy metadata from the typed request.
3. Create a temporary worktree at the exact current agent head.
4. Merge current `main` with `--no-edit` and fail on any conflict. Never auto-resolve.
5. Add only the generated message and audit record.
6. Stage explicit paths.
7. Run `python3 scripts/lint_outbox.py --me chatgpt_1 --fetch --staged` with output and exit code captured separately, never piped as a gate.
8. Assert the staged path set equals the declared generated path set.
9. Commit, push without force, fetch, and verify the remote branch equals the local commit.
10. Write the terminal result comment.

### 5.3 `publish_handoff`

Use two commits because the handoff must pin an already-published artifact commit.

Artifact commit:

1. Perform common preflight and checked merge.
2. Write only declared `chatgpt_1/` artifacts and an audit pre-record.
3. Assert exact staged paths, commit, push, fetch, and remote-verify.

Message commit:

1. Render a handoff with:
   - `artifact_ref: agent/chatgpt_1`;
   - `artifact_commit: <verified artifact commit>`;
   - `artifact_paths: <exact request artifact paths>`.
2. Stage the generated message plus final audit record only.
3. Run fetched staged outbox lint.
4. Assert exact staged paths, commit, push, fetch, and remote-verify.
5. Return both commits.

If the artifact commit succeeds but the message commit fails, the result is `partial_failure`, not success. The audit record and issue comment name the orphan artifact commit. Automatic rollback or force-push is forbidden.

## 6. Idempotency and concurrency

- `request_id` is globally unique within `chatgpt_1` gateway requests.
- Canonical payload serialization excludes issue formatting and includes every semantic request field.
- The workflow concurrency group is `agent-publication-chatgpt_1`; requests are serialized.
- Branch-head compare-and-swap is checked again immediately before each push.
- Push rejection is terminal for that attempt and never retried blindly.
- Workflow retries and manual reruns return the prior result when the request already reached a terminal state.

## 7. Audit record

For every terminal request, write:

```json
{
  "schema_version": 1,
  "request_id": "...",
  "payload_sha256": "...",
  "issue_number": 123,
  "requested_by": "tarstars",
  "actor": "chatgpt_1",
  "operation": "...",
  "base_main_commit": "...",
  "initial_agent_head": "...",
  "artifact_commit": "... or null",
  "message_commit": "... or null",
  "message_path": "... or null",
  "artifact_paths": [],
  "lint_exit": 0,
  "lint_output_sha256": "...",
  "push_verified": true,
  "status": "succeeded | failed | partial_failure",
  "error_code": "stable machine code or null",
  "completed_utc": "server-generated UTC"
}
```

The issue comment contains the same material result. Secrets, tokens, full request bodies, and arbitrary exception traces are excluded.

## 8. Stable failure codes

At minimum:

- `UNAUTHORIZED_REQUESTER`
- `ACTOR_MISMATCH`
- `SCHEMA_INVALID`
- `STALE_MAIN`
- `STALE_AGENT_HEAD`
- `IDEMPOTENCY_COLLISION`
- `PATH_FORBIDDEN`
- `REFERENCE_NOT_FOUND`
- `MERGE_CONFLICT`
- `LINT_FAILED`
- `UNEXPECTED_STAGED_PATH`
- `COMMIT_FAILED`
- `PUSH_REJECTED`
- `REMOTE_VERIFY_FAILED`
- `PARTIAL_PUBLICATION`

Human text may elaborate, but automation keys on these codes.

## 9. Security limits

- Workflow permissions: `contents: write`, `issues: write`; everything else `none`.
- Accept requests only from the configured operator allowlist.
- Fixed repository, actor, branch, and path policy are compiled into the implementation and tested.
- Maximum issue body, message body, artifact count, per-artifact bytes, and total bytes are bounded.
- Request text never becomes shell, ref, workflow path, executable bit, or Git configuration.
- Generated filenames use server time plus a collision-safe suffix when required.
- No request can modify the gateway implementation or workflow.
- No force push, tag creation, release creation, secret access, external network call, or Arena operation.

## 10. Bootstrap and rollout

1. `local_claude_1` creates the canonical task record and assigns the shared write set.
2. `claude_1` implements the script, schema, workflow, documentation, and tests.
3. `codex_1` independently reviews the package and executes the acceptance matrix.
4. `local_claude_1` integrates and deploys the labels/workflow.
5. Shadow test: parse and validate a request but perform no write.
6. Live harmless test: publish a `progress` message to `local_claude_1` under a dedicated gateway test task.
7. Retry the identical issue and prove no duplicate.
8. Read the resulting message through ordinary `inbox_sweep.py` and verify zero delivery errors.
9. Only then mark the gateway available for interactive `chatgpt_1` publication.

## 11. Boundaries

This gateway does not replace `coordd`, task leases, the integrator, review authority, or the Arena controller. It does not make `chatgpt_1` autonomous and does not provide compilation, tests, datasets, or a general execution environment.
