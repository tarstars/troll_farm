Part 0 — Running Rust on this machine (emacs + make)

To try the constructs in Part A you do not need cargo or a project. A single .rs file with a fn main() is a complete program: rustc compiles it to one binary. A two-line Makefile wraps that so the whole loop is edit → make → read output. This machine has rustc 1.75.0 and GNU make already installed — nothing else is required.

The scratch pad (already set up)

Two files live in rust-scratch/: scratch.rs (a runnable file whose examples mirror Part A — &str/String, Vec/HashMap, iterators/closures, Option/match/if let, a struct+impl) and Makefile. Edit scratch.rs, replace the examples with whatever you want to test, and run one command:

# from rust-scratch/ :
make            # compile scratch.rs (edition 2021) and run it — prints its output
make FILE=x.rs  # compile + run some other single file instead
make check      # type-check only (fast) — no binary produced, no run
make clean      # delete the built binary (/tmp/rust-scratch-bin)

The whole Makefile is just a wrapper around rustc — no magic, portable to any Rust box:

FILE ?= scratch.rs
BIN  := /tmp/rust-scratch-bin
run:
	@rustc --edition 2021 $(FILE) -o $(BIN) && ./$(BIN)   # compile then run

Without make at all, the same thing is one line: rustc --edition 2021 scratch.rs -o /tmp/s && /tmp/s. Add -O for an optimized build (as the arena uses); omit it for faster compiles while iterating.

The emacs loop. Open scratch.rs, then M-x compile RET make RET. Output (or compiler errors) appear in the *compilation* buffer; compiler errors are clickable — press C-x ` (or click) to jump straight to the offending line, since rustc's file:line:col messages are exactly what emacs' error parser understands. After the first run, M-x recompile (or bind it) re-runs the same command with no prompts. To make make the default so you never retype it, add (setq compile-command "make") to your config (or set it per-file). Base emacs needs no rust-mode for this — it treats .rs as text and make/rustc do the work (if you want syntax highlighting later, M-x package-install rust-mode).

Why edition 2021: the arena bot and the examples use 2021 idioms (notably inline format args like println!("{x}")). Plain rustc scratch.rs defaults to edition 2015 and would reject those — hence the flag is baked into the Makefile.

Part A — Reading Rust as a C++/Go/Python developer

Rust will feel familiar in the small (C-like syntax, methods, generics) but has three ideas that have no direct analogue in the languages you know: ownership & borrowing (who may read or write a value, enforced at compile time), no null / no exceptions (absence is Option, failure is Result), and explicit copying (nothing heap-allocated is duplicated unless you say .clone()). Everything below is a construct that literally appears in this bot.

A1. The three hard ideas, once

Ownership. Every value has exactly one owner; when the owner goes out of scope the value is freed (RAII, like C++ destructors, but the compiler tracks it). Assigning or passing a non-trivial value moves ownership — the source name becomes unusable — unless the type is Copy (small stack types: integers, char, tuples of those) or you explicitly .clone() it. There is no garbage collector.

Borrowing. Instead of moving, you lend a reference. A shared borrow &T is read-only and you may have any number at once; an exclusive borrow &mut T is read-write and you may have exactly one, with no &T alive at the same time. The compiler's "borrow checker" rejects code that violates this. The pay-off: a value is either shared and immutable or uniquely mutable, which is how Rust prevents data races and dangling pointers with zero runtime cost. In this bot, decide_elite(state: &State) only ever reads the world; the parser takes reader: &mut impl BufRead because reading a line mutates the stream position.

Absence, not null. A maybe-missing value is Option<T> = Some(x) or None; there is no null pointer. A maybe-failing call is Result<T,E>. You must handle both cases, which is why you will see if let Some(x) = …, .unwrap_or(default), and the ? operator everywhere.

Part B — The game and the strategy (what & why)

B1. The game in one paragraph

Two players share a small grid map over ~300 turns with a 50 ms budget each turn. You command "trolls" (workers) that MOVE, HARVEST fruit, CHOP/fell trees, MINE iron, PLANT a carried seed, PICK a banked item back out of your shack, DROP (bank) their load at the shack, or TRAIN a new troll. The map has fruit trees (PLUM, LEMON, APPLE, BANANA), water (which speeds nearby tree growth), and iron. A tree grows one size per cooldown tick, from size 1 up to size 4 (MAX_SIZE); only at size 4 does it start bearing fruit. Felling a size-s tree yields s wood (capped by free carry capacity) and removes the tree from the map — so a half of the board can be permanently deforested.

B2. Why wood — the scoring economics

A player's score is Σ(plum + lemon + apple + banana) + 4·wood banked in the shack; iron scores 0 (it is only a training currency). Wood is leveraged 4×, so a bot that funnels its effort into banked wood out-scores a fruit farmer of equal activity. Every design choice below follows from this one fact.
SpeciesGrow cooldownHealth (base + slope·size)Why the bot cares
BANANA6 (→4 next to water)2 + 1·size — very lowGrows fastest and is cheapest to fell (~2 chops at size 2). The ideal crop. Useless for training, so every banana is pure surplus turned into wood.
APPLE9 (→2 next to water)8 + 3·size — tankyWater-apple grows very fast but is slow to fell; used only as a secondary seed source when standing beside water.
PLUM / LEMON8 (→3)4 + 2·sizeTraining currency (a troll costs n + stat² of each fruit). Harvested only to fund the one chopper, then ignored.

B3. The strategy: two trolls, fixed roles ("gold-elite")

This bot replicates the decoded top-of-Gold meta. It commits to exactly two trolls (GE_MAX_TROLLS = 2) and assigns roles purely by the test chop_power >= 2:

TrollTalents (ms, cc, hp, chop)Job
Starterthe (1,1,1,1) troll you begin with① harvest the fruit types the chopper still needs and MINE iron to fund it (roughly turns 20–77); ② once the chopper exists, run the banana printer (below); ③ if the farm is momentarily stocked, help chop (it has chop 1).
Chopper(2, 2, 0, 2) — trained oncePerma-fell local trees and bank whenever it fills. cc 2 means it is full after 2 wood → very short round-trips. hp 0 (cannot harvest) makes it cheaper to train — it never needs to harvest.

Why not the boss's expensive cc 4 chopper, or 3–4 trolls? Both were measured worse: a cc 4 chopper's lemon cost (n + 16) drains the economy, and every alternative troll count / spec loses the head-to-head production race to the two-troll (2,2,0,2) configuration.

The opening (≈ turns 1–77) funds and trains the single chopper. After that the game is one sustained loop: the starter keeps a dense cluster of fast-growing bananas alive next to the base, and the chopper fells them forever, banking ~40–82 wood by turn 300 (≈ 160–330 points).

B4. The banana printer — the wood engine

The "printer" is a closed loop that keeps a cluster of bananas within farm_r = 3 of the shack (cap farm_max = 12), so the chopper always has a ripe, low-health tree one step away — no travel, no idle.
  1. Seed acquisition: the starter PICKs a banana out of the shack inventory (bananas get banked from felling/harvesting), or, if none are banked, HARVESTs a fruit-bearing banana (or water-apple) tree to obtain one seed.
  2. Planting: carrying a banana, it walks to the nearest free base cell (water-adjacency is a mild tiebreak, since banana cooldown drops 6→4 beside water) and PLANTs it.
  3. Felling: the chopper fells these local bananas, banks at cc 2, and the loop repeats. Banked fruit stays near zero — everything is converted into wood.

B5. ★ The v1.4.5 fix: a protected seed reserve (the crux)

The bug it fixes — the #1 arena loss. The chopper's normal rule is "fell any farm banana at size ≥ 2". But a tree only bears fruit at size 4. If the chopper fells every banana the instant it reaches size 2, no banana ever survives to size 4, so none ever fruits. Fruit is the only new source of banana seeds, so the seed supply only drains. When the last banked seed is spent, the printer has nothing to plant, our half of the map deforests, and — with no tree to fell and nothing to harvest — both trolls park next to the shack and do nothing for the rest of the game. That is the "shutdown" loss the arena kept handing us: ~5 plants left, chopper wandering, ~22 wood banked, a ~115-point defeat.
The fix — a seed reserve. Before choosing targets each turn, the bot marks the K = 2 (GE_SEED_RESERVE) most-mature farm bananas as a protected reserve the chopper is forbidden to fell. Those two bananas are allowed to ripen to size 4, where they bear fruit; the starter HARVESTs that fruit as fresh seeds and replants — closing the loop into a genuinely self-sustaining farm. Every other farm banana is still felled aggressively for wood, so throughput barely drops. The reserve is dropped during end-game "liquidation" (there is no future to sustain, so fell everything).

Measured effect on arena-faithful sparse maps: banked wood rises from ~45 → ~82, idle turns collapse, and the farm survives to the end instead of dying mid-game. Because Gold rank is win-rate driven, converting these shutdown losses into competitive games is pure ranking gain — this was the single change that mattered most for v1.4.5.

Part C — The code, block by block

This walks docs/best-bot-v1.4.5.rs in source order. Each block notes its purpose, the Part-A idioms it leans on, and the Part-B intent it serves. Line numbers refer to the readable file.

C1. fn main and the I/O loop (lines ~837–end)

CodinGame speaks to the bot over stdin/stdout. main reads a one-time header (width height) and the static ASCII map, then loops once per turn: parse this turn's state, decide, print the semicolon-joined commands, flush.

read "width height" // once read `height` map rows → parse_grid // walkable / shacks / iron / water (static all game) loop turns: parse_turn → State // inventories, trees, trolls this turn debug_log (no-op unless DEBUG) // stderr sim-fidelity echo cmds = decide_elite(&state) // ← the whole brain writeln!(out, "{}", cmds.join(";")) // e.g. "MSG v1.4.5…;MOVE 0 2 1"
Why the import reads use std::io::{self, BufRead, Write} — the self. That one line pulls in three things, and they play two different roles:
  • self = the module std::io itself. It is what lets the code write the path-qualified constructors io::stdin(), io::stdout(), io::BufReader::new(…), io::BufWriter::new(…). Drop the self and the name io is simply not in scope — you would have to spell every call std::io::stdin() in full, or add a second line use std::io;. The self inside the braces is exactly that second line, folded in: "also bring the module named by the prefix into scope."
  • BufRead and Write are traits, imported by name. Here is the Rust rule with no analogue in Go or Python: a trait's methods are only callable when the trait is in scope by name — a path prefix is not enough. io::stdin().lock() hands back a reader whose .read_line() / .lines() live on BufRead; writeln!(out, …) and out.flush() are Write methods. Without these two names in scope, those calls would not compile even though the module path already is. (This is also why the parser's signature reader: &mut impl BufRead needs the name — see A6.)
So {self, BufRead, Write} says, in one tidy line: the module (to reach the io:: constructors) plus the two traits (to call the read/write methods). The closest Python is import io (the module handle) combined with from io import BufRead, Write (the names) — Rust merges both into a single use.
  • Idioms: parse_grid is a match ch { '0' => …, '.' => … } over map characters (A4). read_line returns Option<String> and parse_turn propagates end-of-stream with ? (A4); field parsing uses .parse().unwrap(), trusting the referee's format (A4).
  • The static sets (walkable, shacks, iron_cells, water_cells) are parsed once and .clone()d into each turn's State (A2) — the map never changes.

C2. State structs: State, Troll, Tree (lines ~53–106)

Plain records (A3) holding the parsed world. Troll and Tree carry small impl method blocks (A6):

  • Troll::pos() → its (x,y); total_carried() = self.carry.iter().sum(); free_capacity() = carry_capacity − total_carried(). These three drive nearly every "am I full / where am I" test.
  • carry: [i32; 6] is indexed by the item constants PLUM=0 … WOOD=5 (all usize, A7) — e.g. u.carry[BANANA].
  • #[derive(Clone)] (A6) lets decide_elite take a working copy of the troll list (state.my_trolls.clone()) so it can sort it by id without touching the shared State.

C4. Per-turn setup & the training gate (inside decide_elite, lines ~222–255)

At turn 1 the persistent maps are cleared. Then the bot snapshots the shacks, inventory and turns_rem, sorts its trolls by id, and decides whether to train the chopper this turn:

let want_chopper = n < GE_MAX_TROLLS && !my.iter().any(|u| u.chop_power >= 2);
let cost        = training_cost(n, spec);            // n + ms², n + cc², n + hp², n + chop² (iron)
let train_now   = want_chopper && mb_afford(inv, &cost, have_iron);
let need_iron   =
    have_iron && want_chopper && inv[IRON] < cost[IRON] && afford_fruit_only(inv, &cost);
let need_fund: [bool; 3] = [inv[0] < cost[0], inv[1] < cost[1], inv[2] < cost[2]];
  • Idioms: .iter().any(…) (A5) tests "do we already have a chopper?"; the tuple spec is GE_SPEC (A3); indexing inv[IRON] uses a usize constant (A7).
  • Intent (B3): want_chopper is true until one (_,_,_,≥2) troll exists. need_fund[t] is the per-fruit deficit that steers the starter's harvesting; need_iron flags "fruit is ready but iron isn't → go mine".

C5. ★ The seed reserve & the fell_ok gate (lines ~263–283)

This is the v1.4.5 change (B5) and the heart of the file. First, collect the farm's bananas, sort them most-mature-first, and reserve the top K. Then fell_ok — a closure every targeting step consults — refuses to fell a reserved cell.

let mut seed_cells: HashSet<Cell> = HashSet::new();
if GE_SEED_RESERVE > 0 && !liquidation {
    let mut fb: Vec<&Tree> = state.trees.iter()
        .filter(|p| p.tree_type == "BANANA" && manhattan(p.pos(), shack) <= farm_r)
        .collect();
    fb.sort_by_key(|p| (-p.size, -p.fruits, manhattan(p.pos(), shack), p.pos())); // mature first
    for p in fb.into_iter().take(GE_SEED_RESERVE) { seed_cells.insert(p.pos()); }
}
let fell_ok = |p: &Tree| -> bool {
    if seed_cells.contains(&p.pos()) { return false; }   // protected seed source
    if liquidation { return p.size >= 1; }            // endgame: fell anything
    let farm_banana = p.tree_type == "BANANA" && manhattan(p.pos(), shack) <= farm_r;
    p.size >= if farm_banana { GE_FARM_FELL } else { fell_size }
};
  • Idioms: a whole iterator pipeline — .iter().filter(…).collect() into a Vec<&Tree> of borrows (A5, A2); sort_by_key with a tuple key for lexicographic "size desc, then fruits desc, then nearest" (A5); .into_iter().take(K) to keep the top K (A5). fell_ok is a closure capturing seed_cells, liquidation, farm_r, fell_size (A5); early returns make it read like a guard cascade.
  • Intent (B5): "most mature first" guarantees the two bananas closest to fruiting are the ones spared, so the farm reaches size 4 and re-seeds itself.

C6. Target selection: nearest_fell (lines ~337–354)

A representative iterator chain: among all trees, keep the fellable, own-half, in-range, reachable, un-reserved ones, and return the position of the one that is fastest to fell (travel turns + chop turns).

let nearest_fell = |free_needed: bool| -> Option<Cell> {
    if free_needed && u.free_capacity() == 0 { return None; }
    state.trees.iter()
        .filter(|p| fell_ok(p))                                   // C5 gate (respects the reserve)
        .filter(|p| own_half(p) && within_roam(p))
        .filter(|p| d.contains_key(&p.pos()) && !reserved.contains(&p.pos()))
        .min_by_key(|p| {                                          // pick the cheapest
            let steps  = (d[&p.pos()] + u.movement_speed - 1) / u.movement_speed.max(1);
            let chop_t = (p.health + u.chop_power.max(1) - 1) / u.chop_power.max(1);
            steps + chop_t                                          // ceil-divides (A7)
        })
        .map(|p| p.pos())                                          // Option<&Tree> → Option<Cell>
};

  • Intent (B3/B4): "closest and cheapest to fell" — banana health 2+size is tiny, so a ripe farm banana almost always wins, keeping the chopper on the local loop.

C9. Endgame banking & liquidation

Two time-based overrides woven through the cascades: (1) endgame banking — computed per troll as eta = ceil(dist_home / ms) + 1; if turns_rem ≤ eta + 1 the troll banks whatever it holds (B6), because carried goods score 0 at t=300.
