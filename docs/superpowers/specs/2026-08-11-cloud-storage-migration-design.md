## 4. Target architecture

**Bucket layout** (one bucket, e.g. `troll-farm-data`, in `troll-farm-auto`):

- `games/raw/YYYY-MM-DD.jsonl.zst` — daily packs of game dumps plus
  `games/raw/manifest.jsonl` (game id → pack, sha256). Packs, not 15k tiny objects:
  batch analytics is the access pattern; ~10× cheaper and faster to scan. Existing
  corpus ≈ 1–1.5 GB packed.
- `games/parsed/` — parquet/jsonl derived layer, regenerated by the parser.
- `snapshots/` — packed dated snapshots.
- `archive/` — the frozen USB trees, **cold storage class**, uploaded once with
  per-file SHA-256 manifests (same copy-before-delete discipline as the three
  documented tranches in `docs/storage-policy.md`).
- `billing/` — Yandex billing export, enabled at Phase 1, so the agent can watch
  spend without the owner.

**Collector v2 on the VM:** the existing read-only collector logic runs on the VM
24/7, writing packs + manifest to S3 (VM↔S3 traffic is intra-cloud). One check during
implementation: whether the collector's public REST reads need the session cookie
that lives on `project_host`; if yes, provision it to the VM the same way as the
coordd token. The `project_host` 05:17 cron stays as a parallel replica until the VM
collector is proven (same both-run-compare discipline as the shadow runbook), then
retires or stays as a secondary.

**Read layer:** GeeseFS mounts the bucket at the `medium_data` path on BOTH machines
— frozen-analysis seal tests become runnable on the VM too, and the USB stops being
live infrastructure. `cgauto/check_external_storage.py` gets a v2 that verifies the
bucket mount instead of an ext4 filesystem label.

**Processing:** DuckDB on the VM against S3 for corpus analytics; YT from the
workstation for >1 h batches when it is up; preemptible bursts (≤28 vCPU today)
for cloud-side heavy runs — after the grant period resets.

## 5. Phases (each verify-then-cut; nothing deleted until digests match)

- **Phase 0 — prerequisites:** owner sets the 17,000 ₽ budget alert; owner glances at
  what consumed the non-VM ~7,500 ₽ this period (console → detailed consumption).
- **Phase 1 — bucket + game DB:** create bucket + static S3 keys (stored beside the
  SA key, never in git); enable billing export; pack and upload the existing corpus
  with manifest; verify by count/bytes/sha256. Cost: tens of ₽/month.
- **Phase 2 — collector v2:** deploy on the VM, run in parallel with the local cron,
  compare a few days, cut over.
- **Phase 3 — cold archive:** with the USB attached once more, upload the frozen
  trees to `archive/` (cold class), verify manifests, demote the USB to offline
  backup.
- **Phase 4 — read layer:** GeeseFS mounts on both hosts; storage preflight v2;
  confirm the frozen seal tests pass on both machines through the mount.
- **Phase 5 — docs:** `docs/storage-policy.md` v2 and the `AGENTS.md` short version
  updated under the doc-budget discipline; the YT/burst compute rule recorded.

## 6. Non-goals

No managed ClickHouse/PostgreSQL; no GPU work (quota 0, unrequested); no YT
migration (YT keeps its mirror role); no history rewriting; no change to what stays
in git (code, protocols, results, compact records — per the existing storage policy);
no burst compute before the grant period resets.
