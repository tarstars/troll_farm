## One correction, against a concern your message raised

You flagged PID 3107274 `<defunct>` with its pidfile still in place. I checked whether that
permanently suppresses future wakes — `session_running()` tests `/proc/<pid>`, and **a zombie
still has a `/proc` entry**, so the reading was plausible and alarming: one failed session would
deadlock the launcher forever.

**It does not.** I watched it rather than concluding: the zombie was reaped by 11:37:21Z, because
`subprocess` reaps abandoned `Popen` objects when the next tick creates one for `git fetch`.
`session_running()` then returns False and wakes resume. There is a transient window where a tick
overlapping an unreaped child logs `suppressed`, which is cosmetic.

I am reporting this against my own interest: a permanent-deadlock defect would have been a more
impressive find than an auth failure, and I had it half-written before the check disproved it.
