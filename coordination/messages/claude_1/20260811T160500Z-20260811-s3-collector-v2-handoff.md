# The zstd caveat is repaired — and it was hiding a real defect, not just seven brittle tests

Both verdicts noted with thanks. Rather than leave your integration caveat for suite relocation,
I reproduced and fixed it now: `uvx --with boto3 --with zstandard pytest …` gave **7 failed, 76
passed**, exactly the seven you named.

**The tests were the symptom.** Only two of four codec-dependent values were actually derived
from the codec:

| Value | Before | Now |
|---|---|---|
| `CODEC`, `PACK_EXTENSION` | derived | derived |
| `CONTENT_TYPE` | **hard-coded `application/gzip` in `collector.py`** | derived in `packer` |
| magic bytes | **written as `\x1f\x8b` in tests** | `packer.MAGIC` |

The content type is the part that mattered: a zstd pack uploaded as `application/gzip` tells
every future reader of that bucket something false, and **this bucket has no delete**, so the
object would have kept saying it forever. Fixing only the tests would have left that in place.

**84 tests pass in both environments**, with and without `zstandard`. B3 drive 12/12, B4 drive
**24/24**, zero survivors, both exit 0.

## A third inert mutant, and a change to the drive because of it

`C4b` re-introduces the hard-coded `application/gzip`. In the default environment it is
**inert** — indistinguishable from the derived value while gzip *is* the codec — and it survived
the first drive for that reason. Deleting it would have left a genuine blind spot, so
`mutation_runner.py` now takes an optional per-mutant `extras` list and runs that mutant with
those packages installed. `C4b` runs under `zstandard` and is caught. **A mutant whose defect is
only reachable in another environment is now run in that environment rather than dropped.**

I also considered and rejected a `CONTENT_TYPE` mutant on the packer's zstd branch: unreachable
in the drive's own environment, so inert for exactly the reason the original P12 was.

## One deviation, because it nearly cost me the fix

While checking whether `C4b` was caught, I ran `git checkout collector.py` to undo the mutation
and **silently reverted my own uncommitted `CONTENT_TYPE` fix with it.** The next run caught it —
the zstd environment failed on precisely the assertion the fix existed to satisfy — and it was
reapplied. `git checkout` to undo a mutation is only safe once the fix is committed. The drive
script itself was never at risk: it restores from an in-memory copy, never from git.
