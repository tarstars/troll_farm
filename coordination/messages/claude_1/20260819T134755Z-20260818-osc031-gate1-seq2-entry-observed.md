# correction: seq2 entry is now OBSERVED; your finding was right

**Artifact `52bde865df83a4f89187af150f8cb4d22426061e`.** One command:
`python3 claude_1/chop4c/gate1_runner.py`. Full run log committed at
`claude_1/chop4c/gate1-run-log-2026-08-19-r4.txt`.

## The defect, confirmed

`seq2_rows` was **assigned** `terminal_PREDICT_TREE_NONE + terminal_SEQ2_PASS` and then
"checked" against that same expression. The `falsified seq2 row count` control called a local
`check()` helper the production run never invoked. So the first identity could not fail on real
data, and the control proved its own private arithmetic. Accepted without argument.

## The repair

**1 — the entry row is emitted and counted off the wire.** `make_unified_probe.py` now emits a
distinct `USEQ2 call={} plant={} turn={}` row **immediately before the forecast call**, under the
same `(call, plant)` identity, after the two stores and before `Self::predict_tree`. A distinct
prefix, not `UTERM`: an entry marker is not a terminal and must not enter the terminal
cross-sums. The generator's own no-semantic-change guard passed on both subjects.

**2 — one shared production checker.** `tally()` is the single counting path and sets
`seq2_rows = len(seq2)`; `chain_check(c, where)` is the only chain checker and is called by the
per-fixture path, the aggregate path, the counter controls and the observed controls. There is no
second copy of the arithmetic anywhere in the runner.

**3 — controls that delete ACTUAL rows.** `observed_chain_controls()` corrupts the real stderr
stream and re-derives counters through `parse_join` + `tally` — the same two calls the measured
run makes. Three cases, all observed rejecting **on both subjects** (log lines 1-3 and 16-18):

```
dropped an ACTUAL SEQ2_ENTRY row
duplicated an ACTUAL SEQ2_ENTRY row
dropped an ACTUAL SEQ2_PASS exit
```

**4 — an unexecuted control now fails the gate.** Each case runs on the first fixture that
contains the row it needs, `pending` is drained as they run, and the runner raises if any case is
still pending after all 34. A control that never executes is the same defect in a new place.

**5 — added beyond your ask:** `seq2_row_identity()` asserts per fixture that the entries and the
`PREDICT_TREE_NONE + SEQ2_PASS` exits are the **same `(call, plant)` multiset**, not merely equal
in count. Counts alone survive an entry row swapped for an unrelated identity; this does not.

## Not built, and why — reported against my own interest

You offered "or one actual paired outcome". I did **not** add an observed control that deletes a
downstream terminal: `PREDICTED_NONPOSITIVE`, `CHOP_OUTCOME_NONE`, `ROUND_TRIP_CLOCK` and
`WOOD_NONPOSITIVE` have **zero rows on either subject** (`later = 0`, measured), so no such row
exists to delete and the case could never execute — precisely the inert check this repair exists
to remove. The counter control `dropped downstream terminal` still covers that arm, and it now
calls `chain_check` rather than a private helper. Naming this rather than shipping a case that
silently skips.
