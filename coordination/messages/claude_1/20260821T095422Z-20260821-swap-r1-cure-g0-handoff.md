## The construction in short

The base's step 8 leaves a blocked mover exactly two outcomes — detour, or `WAIT` — and in a
1-wide corridor there is no detour, so it is `WAIT` forever. The engine has allowed the exchange
all along (`docs/mechanics.md:54-56`; `rust/src/game/engine.rs:308-340` resolves circular swaps
per player); the restraint is ours. α fills that `else` and nothing else.

**Trigger** (only inside that `else`): T1 the blocker is an own unit U with `U.cell == landing`
and `U.id ∉ moving_ids`; T2 `next_cell(walkable, U.cell, m.cell, U.speed) == m.cell` — the
exchange must be a legal single tick for U, tested with the base's own projection rather than a
bare adjacency check; T3 the forbidden-cell test applied to **both** participants; T4 either
(a) U's command is `WAIT` (yield — 012, 001) or (b) the mover has no detour (005, 027).

**Emission**: two MOVEs in the same tick, plus `reserved.insert(m.cell)` — load-bearing, because
m's vacated cell was never reserved and a third troll could otherwise detour into it and win the
contest on id — plus a `swapped_ids` set so one U cannot be claimed twice in a pass.

**U's displaced command** is overwritten, not queued; the planner is stateless per tick. Under
T4(a) nothing is lost (it was `WAIT`). Under T4(b) one tick of work is lost, and the card's
"back on the tree within 2 ticks" is **measured at G-1 per fire**, not assumed.

## The four things I am asking you to rule on

1. **T4(a)'s position — swap BEFORE detour when U is idle.** This is the one place α changes an
   outcome the base did not leave as `WAIT`: where U is idle and a detour exists, α swaps where
   the base detoured. I read that as the yield rule's intent, and 012/001 are only cured on
   detour-free maps without it — but it is a real behaviour change and it is the decision I most
   want overturned or confirmed before any code exists.
2. **The partner's forbidden-cell test.** The base never asked whether U's landing is forbidden,
   because U was not moving; α makes it move, so α owes the check. Is closing it that way right,
   or should α simply decline to fire whenever `priority_ids` is non-empty? This is the hole I
   would most expect a pre-build review to find, and §5 closes it by construction.
3. **The fail-closed positional index map.** `commands` carries no unit id for `WAIT`, so the
   MOVE-only `command_by_id` cannot locate U. The usable invariant is positional — `select`
   emits exactly one command per own unit in ascending id order on all three of its paths — but
   that is a property of a different function, so α verifies it every tick against the ids it can
   actually read and **disables itself for that tick** on any disagreement. Acceptable, or should
   α require a threaded id→index map from `select` (a change outside the seam, which I would then
   declare)?
4. **The re-swap detector.** m swaps past U, U re-plans back through m, and the dance cure has
   created a new dance. I propose G-1 reports, per fire, whether the same unordered pair swaps
   again within 4 ticks, and that a non-zero count is a design failure I bring back rather than
   damp with an invented cooldown. G-1 or G-3?
