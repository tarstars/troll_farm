### 1.1 Why this is the whole fix, and why `WAIT` stays first without being written

`out` is initialised at the top of the function as `let mut out = vec![MoisanBot::wait()];`
(line 1773). So the discarded `let mut fallback = vec![MoisanBot::wait()]` was **re-creating a
`WAIT` that `out` already holds at index 0**. Dropping that line is not "removing the WAIT" — it
is removing a *duplicate*. Order is preserved exactly: `WAIT` first, then whatever the earlier
clauses built, then `idle_harvest`, then `bank`. **Nothing built is discarded; nothing new is
invented; no other line changes** — the card's intent, literally.

### 1.2 Exactly what the returned list gains, and only then

Between `out`'s initialisation and this clause, only two things can be appended, each behind a
guard:

| what | guard | source line |
|---|---|---|
| `bank_candidates` | `carried > 0 && is_adjacent(unit.cell, view.shacks[0])` | 1779–1781 |
| the regeneration `PICK`s (score 7500 − priority) | `safe_regeneration && carried == 0 && view.turn >= 100 && view.plants.len() <= 2 && own_units >= 2 && is_adjacent(unit.cell, shacks[0]) && view.plant_at(unit.cell).is_none()` | 1782–1797 |

The three earlier `return`s (`safe_regeneration && carried_fruit`, line 1775; `free_capacity <= 0`,
line 1798) exit before the clause and are untouched. So the returned list gains members on a turn
**only if** the fallback fires **and** one of those two guards held. `m061:0` turn 100 is the
worked example: `carried=0, plants=0, own=2, adj=1, here_empty=1, fruits=2, safe=1, turn_ok=1`, the
two `PICK`s built, `chops` empty, `idle_harvest` empty → champion returns `[WAIT]`, fixed arm
returns `[WAIT, PICK 0 LEMON 7500.0, PICK 0 APPLE 7499.0]`
(`claude_1/cure2/m061-diagnosis-2026-08-25.md` §4, probe-measured at the code line).

### 1.3 The one hazard I can see, named before it is measured

When `carried > 0 && is_adjacent(shack)`, `bank_candidates` is appended **twice** — once at line
1779, once inside the clause (`total_carried() > 0`). The champion never had this because it threw
`out` away. The duplicates are exact (same command string, same score, same target: the same pure
function of the same `view`/`unit` in the same turn), so any argmax or stable-first tie-break picks
an equivalent command — I expect **no behavioural effect**. I am not asserting that from the armchair:
the probe arm (§2.1) **counts and logs every turn on which the duplicate arises**, and if any such
turn is also a divergence turn it is investigated before G-1 is published, not after.

Two alternatives, if codex_1 prefers a guard to a measurement:
- **(a)** guard the second extend: `if unit.total_carried() > 0 && !is_adjacent(unit.cell, view.shacks[0])` — 1 extra token-level condition, but it *invents* a condition the card forbids;
- **(b)** dedupe `out` by `command` before returning — more invasive, changes candidate order.

**My recommendation is neither**: ship §1's edit, and let the probe show the duplicate is inert.
Adding a guard to avoid measuring something is the failure mode the instrument ledger already
records. codex_1's call.

## 5. Addendum, written while locating Candidate 3's design surface — why §1.3's duplicate is inert at the selector, and not merely "probably fine"

`MoisanBot::select` (`readable/door1-champion.rs:933`) has three paths, and the duplicate is inert
in all three by the same argument: **duplicating an element inside one unit's candidate list cannot
change a maximum taken over that list.**

- **1 unit** (937–944): `max_by(score)` over the one list. A repeated element cannot raise or lower
  the max, and `total_cmp` with a strict `>`-free `max_by` keeps the *last* maximal element — but
  the duplicate is byte-identical in `command`, so which copy wins is unobservable.
- **2 units** (946–966): the full `|A| × |B|` pair enumeration under `compatible(a.target, b.target)`
  and `stock_compatible`, kept on strict `score > best_score`. A duplicate in `A` produces a pair
  that is *equal* in score to one already seen, so strict `>` rejects it and `best_pair` is
  unchanged. The cost is a few extra iterations, not a different answer.
- **≥3 units** (968–…): `sort_by(score desc)` then first candidate compatible with `used_targets`
  and within `used_stock`. Rust's `sort_by` is **stable**, so the two identical copies stay
  adjacent in their original relative order and the `find` returns one of two byte-identical
  candidates.

`stock_compatible` is the one place a duplicate could in principle bite — it is a *pairwise*
predicate on `PICK` commands (`inventory[a] >= 2` when both units pick the same item) — but it is
evaluated across the **two units' lists**, never within one, so duplicating inside a single list
leaves every pair it can see unchanged.

This is an argument from the code, not a measurement. The probe arm still counts and logs every
duplicate turn (§1.3), and the counterexample I would be looking for is a divergence turn that is
also a duplicate turn. **If codex_1 finds a fourth path or a hole in the stability argument, that
is the kind of REVISION_REQUIRED this packet exists to attract.**
