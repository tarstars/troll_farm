## Binding design, point by point

1. **Set built from S3 manifests** — `backfill-*.jsonl` plus `daily-*.jsonl` including
   `.rerun-N`. Verified live: 15,291 ids from the backfill.
2. **Rebuilt every run, never cached.** A test asserts the cursor contains no known-id cache.
3. **Skip before fetching.** A test pins that a held candidate never reaches the fetch loop, and
   another that the cap applies to the *remainder* — I verified both fail against the pre-dedupe
   code before keeping them.
4. **Fail loud if the set cannot be built.** Distinct exit code **4** and a `known_ids.failed`
   marker; a test asserts no game is fetched on that path. An empty manifest listing is an error,
   not an empty set — "the bucket lists nothing" and "we hold nothing" are different claims.
5. **Oldest-first among un-held candidates** — accepted as you reasoned it, and pinned by test.
   I have no data that contradicts it: my own B1 measurement is that games leave from the far
   end of the window, so the oldest un-held candidate is the one nearest to expiry.
6. **An empty remainder is a success** — `exit=0` with an explicit `fetched=0`, and no empty
   daily object is written.

## Where I deviated from the design, and why

**Point 6, in implementation only.** I first wrote an early-exit branch for the empty-remainder
case. The mutation drive killed it: replacing `raise _NothingToDo` with `pass` changed nothing
observable, because the ordinary path *already* fetches nothing, packs nothing and uploads
nothing when the remainder is empty. The branch was pure duplication — and worse, it recorded
the run twice in the cursor. **I deleted it rather than adding a test to defend it.** What
remains is the explicit `fetched=0` marker, which is the part that carries meaning, plus a test
that a nothing-new run is recorded exactly once. The behaviour you specified is unchanged.

One related change: a run with nothing to upload now still records itself in the cursor's run
history (with `collected: 0`, so nothing is marked seen). "The collector ran and found nothing
new" is worth having in the history rather than looking like a run that never happened.

## Limits, stated

- **Membership is by game id only.** A held-but-corrupt object counts as held. The manifests
  carry `sha256` and `size`, so an integrity pass is possible later; **nothing here proves the
  stored copy is good**, and the skip should not be read as if it did.
- **Deduplication is against S3 only**, per your scope call — not against `project_host`'s local
  corpus. A game the notebook holds but S3 lacks still gets fetched, which is the migration
  working.
- The `new_ids_from_backfill` / `new_ids_from_daily` stats are **incremental contributions in
  read order** (backfill sorts first), not membership counts. On 2026-08-11 daily contributed 0,
  which is the whole reason this task exists; after the first post-dedupe run it reads 1.
- Cohort 50 discovery takes ~40 s against the platform, most of it the 50 paced battle-list
  reads. Well inside the unit's 1800 s timeout.
