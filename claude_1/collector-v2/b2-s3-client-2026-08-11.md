## Implementation decision: stdlib SigV4, boto3 only as a test oracle

The plan says stdlib-preferred and allows boto3 via `uv`. boto3 **is** installed here (1.34.46),
and I still wrote the signer against the stdlib: the frozen collector this service sits beside
is urllib-only, and collector v2 runs unattended from a systemd timer, where each third-party
import is one more thing that can break at 05:47 with nobody watching. boto3 earns its keep in
the tests instead, as a second implementation of SigV4 to disagree with. Nothing at runtime
imports it.

Credentials load only from `~/.config/troll-farm/s3-keys.json`, in the
`yc iam access-key create --format json` shape. `Credentials.__repr__` and `__str__` are
overridden to redact, so a secret cannot reach a traceback or a log line by accident, and the
loader **refuses** a key file that is group- or world-readable rather than warning about it.

## What the tests actually prove — and what they do not

The differential compares every canonical request against botocore's `S3SigV4Auth`, and
`test_full_signature_matches_botocore` compares the final signature, so the whole chain
(canonicalisation → string-to-sign → signing-key derivation → HMAC) is pinned against an
independent implementation.

**The differential does not cover path encoding, and I found that by mutation rather than by
reading.** The first suite passed 18/18 while the implementation was mutated to drop `~` from
the unreserved set. Cause: botocore's S3 signer takes the URL path **already encoded**
(`S3SigV4Auth._normalize_url_path` returns it untouched, because S3 does not re-encode), so
feeding it a URL this client built means both sides share this client's encoding — the
comparison is structurally blind there. Path encoding is now pinned to RFC 3986 directly
(every ASCII byte: literal iff unreserved, else uppercase `%XX`), which is spec-derived and so
not circular.

That first `~` mutant turned out to be **inert**, not a surviving defect: CPython's
`urllib.parse.quote` never encodes `ALPHA/DIGIT/-._~` whatever `safe` says, so the edit changed
no behaviour. An inert mutant is not a check, so it was replaced with one that really does
mis-encode (`+` treated as safe), and that one is caught.

Two mutants exposed genuine test gaps, both now closed and both re-verified as caught:

- **M5** header values not whitespace-collapsed — no test used a header with interior
  whitespace, so the canonicalisation rule was never exercised.
- **M8** signing key skipping the service step — every test compared pre-signature material
  only, so the HMAC chain itself was unpinned. This is what prompted the full-signature test.

Final drive: **10 defined, 10 applied, 10 caught, 0 survivors, exit 0.** The runner's exit
status describes the experiment (`1` control not green, `2` survivors, `3` a pattern no longer
matches and the drive is incomplete), so a stale mutation cannot report a silent pass.

## The finding that matters for B3/B4: append-only is not what the grant provides

The plan's object layout is described as "append-only by construction", resting on the service
account holding `storage.uploader + storage.viewer` and no delete right. Measured against the
live bucket:

| Operation on my own probe key | Result |
|---|---|
| `DELETE` | **refused**, HTTP 403 `AccessDenied` — as designed |
| plain `PUT` to the same key | **succeeded**, HTTP 200, new ETag |
| `PUT` with `If-None-Match: *` | **refused**, HTTP 412 `PreconditionFailed` |

**The grant stops deletion; it does not stop overwriting.** An object can be silently replaced
by a second PUT to the same key, so "append-only" holds only as long as no code ever reuses a
key. The good news is the second row's remedy: this endpoint **does** honour `If-None-Match: *`,
so B3/B4 can make the guarantee real rather than assumed. My intent unless you rule otherwise:
every collector upload goes through `put_object(..., if_none_match=True)`, and a
`PreconditionFailed` is treated as a genuine error to surface, not as a benign "already there" —
that is exactly the collision the plan's re-run naming (`daily-YYYY-MM-DD.rerun-N`) exists to
avoid, and I would rather learn about it loudly.
