# Round-34 contract — delete the never-read `GameState.scores` field (immutable)

Written before candidate generation. **Newly discovered block** from the post-round-33 scan;
a class the programme had never examined (struct fields that are written but never read).
Notably the Rust compiler does **not** flag it: constructing the field in a struct literal
counts as a use for the dead-code lint, so every prior zero-warning compile was consistent
with this field being dead.

- Parent:
  `claude_1/e7a-incremental-simplification/candidate-r33-delete-minimum-speed-param.rs`,
  SHA-256 `0948eaec18253a09341c3264739260cdeb990c1cd54ddd0d50a57f8c78fc2bba`
  (round 33: all four gates exact).
- Named block: the `scores` field of `GameState`, its per-turn initializer, and the protocol
  module's `score` import that only the initializer used.

## Invariant

1. `scores` occurs exactly twice in the parent: the field declaration `pub scores:[i32;2],`
   and the initializer `scores:[score(&inventories[0]),score(&inventories[1])],` inside
   `read_turn`. There is no read anywhere — no `.scores`, no pattern binding, no
   serialization (machine-verified).
2. Within `mod protocol`, `score` is referenced only by `use super::rules::score;` and that
   initializer; the function itself lives in `mod rules` and keeps its other consumer,
   `MoisanBot::endgame`, which calls `score(&view.inventories[0])<score(&view.inventories[1])`.

## Replacement (exact)

- `pub scores:[i32;2],` → deleted;
- `scores:[score(&inventories[0]),score(&inventories[1])],` → deleted;
- `use super::rules::score;` → deleted (unused once the initializer is gone).

## Supported-state argument

A field that is never read cannot influence any command. Removing its initializer removes two
`score()` evaluations per turn over the parsed inventories; `score` is a pure function of its
argument (a sum of inventory slots), so dropping the calls has no observable effect. The
struct is neither serialized nor compared as a whole — `GameState` derives only `Clone`,
`Eq`, `PartialEq`, and no equality comparison of whole `GameState` values exists in the
program, so the narrowed field list cannot change behavior.

## Rejection condition

Reject if either `scores` anchor count differs; if `scores` or the deleted import survives;
if `score` loses either `endgame` call site or its definition; if the candidate is not
strictly smaller; or if any of the four gates fails.
